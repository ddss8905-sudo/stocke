# 224-Day Opening Gap Detector

This is an opening-price event detector, independent of daily/weekly trend and
reversal screens. It never places orders or assigns portfolio position sizes.

## Exact Rule

Use 224 valid completed trading-session closes through the previous exchange
session. Previous close must be <= their SMA224. Today's regular-session open
must exceed both the previous close and `(sum(previous 223 closes) + open)/224`.
Comparisons use unrounded prices, with floating-point equality tolerance only.
No minimum gap percentage, RS filter, volume confirmation or regime veto is added.
An intraday high/close crossing without an opening crossing does not qualify.

The event stores both averages, open, previous close, source, observation time and
detection time. Later price declines never erase the original opening event.
Changes to opening prices mark records for review/correction; a stale or
split-adjustment-mismatched previous close is not treated as a valid gap.

## Coverage and Sources

Initial coverage is the existing liquid universe, NOT every listed stock:
NASDAQ up to 500, KOSPI up to 200, KOSDAQ up to 200 (its existing fallback list
may be smaller). The preselected universe is frozen during baseline preparation;
the ordinary strategy's final candidate/RS filters are not reused.

US quotes use Yahoo regular-session daily bars with `includePrePost=false`, a
matching current market date and a regular-market timestamp after the open.
This is not an exchange-certified real-time Opening Cross feed. Korean opening
quotes use KIS KRX-only short daily ranges containing the previous and current
business dates, not the long full-history download and not NXT/integrated quotes.
Both KOSPI and KOSDAQ baselines also use KIS KRX histories. The ordinary KOSDAQ
screen's pykrx/Naver historical prices are not mixed with KIS opening prices;
legacy gap baselines without that source marker are rebuilt once.
No current-day bar/volume means pending rather than a guessed opening price.

Korean adjustment rounding <=1 KRW can widen high/low only, preserving open/close.
Larger OHLC inconsistencies, missing/duplicate/invalid dates and insufficient
history are excluded. The latest historical date must match the expected prior
exchange session. A live previous-close disagreement (Korean integer closes must
match, with only a tiny float tolerance in the US) suspends evaluation until the price basis is
reviewed/refreshed. Corporate actions are not inferred from price moves alone.

## Operation

Workflow: `.github/workflows/gap224.yml`, Python 3.11 with
`pip install -r jobs/requirements-gap.txt`. Existing workflows and database rows
are unchanged. No SQL migration or new Supabase privileges are required.

Automatic schedules use IANA zones and `exchange_calendars==4.13.2` for trading
days and US DST. KRX preparation: 08:07 KST; probes: 09:05/15/30 and 10:05/15/30;
final comparison and next baseline: 16:55 KST. US preparation: 08:17 ET; probes:
09:35/45 and 10:00 ET; final comparison and preparation: 17:25 ET. Calendars are
community-maintained and can miss special sessions: dated positive-volume KIS
bars, the 10AM retry window, and the Korean 16:45 minimum daily-data cutoff are
additional guards. Exchange emergency closures/time changes still require
operational review. GitHub schedules can be delayed/dropped/disabled; these are
best-effort probes, not guaranteed alert delivery times.

The first scan bootstraps a missing baseline, which can take around the existing
full-universe collection time; subsequent scans reuse it. Long KIS history calls
are kept out of ordinary morning scans. Scan state distinguishes waiting, running,
preparing, partial, complete, failed and closed. Storage failures never produce
fabricated sample events or a successful zero-event result.

All supported jobs serialize by market using the same concurrency group. Do not
launch independent concurrent CLI delivery workers outside that group. A delivery
object is atomically created without upsert before any first message is sent.
Confirmed sends are not repeated. Telegram 429 responses respect retry-after;
known failures have bounded retries. Timeout, connection failure, invalid JSON or
a crash after claiming leave unknown/sending status and are NOT automatically
resent: check the actual chat before operator recovery. Exactly-once delivery
cannot be guaranteed across a remote API and Storage. A scan can save valid data
but finish with exit code 2 to flag an unconfirmed Telegram delivery.

Private paths under the existing `stocke-sector-strength` bucket:

```
gap224/{market}/baselines/{reference_date}.json
gap224/{market}/{session_date}/events/{ticker}.json
gap224/{market}/{session_date}/charts/{ticker}.json
gap224/{market}/{session_date}/deliveries/{ticker}.json
gap224/{market}/{session_date}/summary.json
gap224/{market}/latest.json
```

Opening events and first-detection charts are immutable after creation; summary
state can change. The chart shows the MA224 series, a separate frozen opening
threshold, and the original opening marker. A later quote is not substituted for
the snapshot's close. Authenticated reads use no-store/no-cache; Storage's mutable
summary indexes are not intended to be transactionally consistent with every
individual upload during a running scan.

## Connect the Existing Telegram Bot

Set these repository **Actions secrets**, not public environment variables:

1. `TELEGRAM_BOT_TOKEN`: the existing bot token.
2. `TELEGRAM_CHAT_ID`: the intended private chat/group/channel ID.

Use https://github.com/ddss8905-sudo/stocke/settings/secrets/actions . Do not paste
values in chat, commits, issue bodies, workflow inputs or command-line arguments.
Only the worker receives these two secrets; Vercel does not need them. Reuse the
existing `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` and KIS Actions secrets.

The recipient must have started the bot (or added it to the intended chat with
appropriate posting permission). Reuse the intended chat ID from the bot's
existing configuration. Do not delete an existing webhook or consume/acknowledge
the existing bot's update queue just to discover an ID. Stocke only calls
`sendMessage`, and does not change webhook/privacy settings.

In GitHub Actions, open **Scan 224-day opening gaps**, choose **Run workflow**,
select one market and `mode=test-telegram`. This sends an explicitly labeled test,
not a stock signal. A successful run confirms Telegram API acceptance; also check
the intended chat. Then use `mode=scan` or the site's gap scan button.

No alert before both secrets are configured is claimed as delivered. The dashboard
shows connection setup required until a worker reports the configuration.

## Verification and Limits

Tests cover exact inequalities, floating equality, no future-close dependence,
intraday-only breakouts, insufficient/stale bars, frozen event charts, later
declines, corrected opens, adjustment mismatch, partial provider failure,
atomic create conflicts, duplicate suppression, Telegram timeout/429 handling,
holidays and US DST. No profitability or out-of-sample investment performance is
claimed; present-day liquid universes have selection/survivorship limitations.
